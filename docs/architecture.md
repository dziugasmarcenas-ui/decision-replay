# Architecture and tradeoffs

## The problem

A numeric result can remain unchanged while its supporting evidence becomes invalid. Replacing a green status with a red one loses the distinction between what was known when a proposal was made and what later became known. This example preserves both.

The demo has three layers:

1. `normalizeExports` validates two unlike CSV schemas and a JSON reference document, resolves aliases, and produces events with source provenance.
2. The pure engine replays a log prefix, evaluates eligibility, records proposal snapshots and human dispositions, and derives correction impact.
3. `app.js` renders those results and appends scenario actions. It does not maintain a separate decision model or call a backend.

## Event contract

Every event has an `id`, `type` and `at`. Imported identifiers are unique across all three sources. Imported records carry `source: {file, rawId, sha256}`; part-specific records also retain `rawPart`. Action IDs are assigned within this synthetic run.

| Type | Additional fields |
| --- | --- |
| `specification` | `floorPct`, indexed by wavelength |
| `calibration` | `validFrom`, exclusive `validUntil`, `instrumentClass` |
| `coating_complete` | `partId`, `coatingRun`, `recipeRevision` |
| `spectral_test` | `partId`, `instrumentClass`, `calibrationId`, `specRevision`, `transmission` |
| `shadow_proposal` | `partId`, `snapshot`, `basisEventIds`, `ruleVersion` |
| `human_disposition` | `partId`, `proposalId`, `disposition`, `note` |
| `calibration_correction` | `calibrationId`, `invalidFrom`, `note` |

The engine accepts validated imported events and actions generated by its own append functions. It is not a validator for arbitrary externally supplied event JSON. Object freezing in tests checks that functions do not mutate their inputs; it does not make browser memory a secure audit store.

## Two notions of time

**Recorded order:** array position says when this demo learned something. `replay(events, through)` consumes only that prefix. The importer writes reference records, then coating records, then measurements; it does not claim to reconstruct real arrival times.

**Effective time:** a calibration's `[validFrom, validUntil)` interval must cover the measurement. A correction's `invalidFrom` may precede the measurement even though the correction was appended later.

Scenario actions use fixed recorded timestamps so runs remain reproducible. This is a single deterministic story, not a general bitemporal database. Explicit time zones are required. Calendar dates are checked before `Date.parse` so normalization cannot silently turn 30 February into a March date.

## Eligibility is separate from human disposition

`evaluate` requires a coating event, a measurement after coating, a specification effective at measurement time, matching calibration class, calibration coverage, no applicable correction, and finite values for all nine required wavelengths.

- `release`: all required evidence is present and all invented limits are met.
- `hold`: supported measurements fall below a limit.
- `abstain`: missing or invalid evidence prevents establishing eligibility.

The first blocking condition supplies a stable reason code. “Release eligible” in the interface is an advisory rule result, not shipment authorization. A human hold is separately recorded and remains visible regardless of subsequent eligibility. No combined production release state is implemented.

## Preserve the original decision

`appendProposal` stores the evaluation result, its evidence IDs and `RULE_VERSION`. `appendHuman` links a disposition to the most recent proposal for that part and rejects a second human action against that same proposal. Append functions return a new log array without editing earlier events.

`impact` starts from a proposal's calibration and original measurement, checks whether the correction covers that measurement, and verifies that current eligibility is blocked by that correction. An unrelated measurement failure does not become a calibration-impact finding. A proposal already made under the same corrected evidence does not become a new affected proposal.

This deliberately narrow impact model is not a general historical dependency graph: superseded measurements and a restored current eligibility can require additional review rules in a production design.

## Why plain JavaScript

The domain engine can run in Node and a browser without adapters. The interface is small enough for native DOM APIs; a framework would add machinery without improving this example's core reasoning. A static site also makes the whole demonstration runnable without keys, hosted databases or paid services.

The tradeoff is manual DOM rendering and no static type checker. Rendered source-derived strings are escaped or assigned with `textContent`. Native selects, buttons, a range input, live announcements and a chart-value table provide keyboard and text alternatives. Browser checks are useful evidence, not a formal accessibility certification.

## Verification strategy

Tests concentrate on externally meaningful invariants: an unsupported result cannot release; invalid input cannot silently become a usable number or timestamp; historical prefixes are deterministic; corrections preserve earlier proposals; unrelated records do not enter an impact report.

Delivery tests build to a temporary directory and inspect actual file contents. The loopback preview server uses the same runtime allowlist and rejects requests for repository metadata, scripts and unrelated paths. The static deployment includes no server; GitHub Pages controls its HTTP headers.

## What production would still need

Authenticated actors and physical instrument identities; durable transactional storage; schema evolution; multiple source revisions and ingestion ordering; idempotency and concurrency; cryptographic trust where required; organization-approved requirements and calibration governance; broader impact semantics; authorized review and release workflows; observability, backups and operational validation.

Those are explicit gaps. The demo demonstrates the modelling decision, not completion of that infrastructure.
